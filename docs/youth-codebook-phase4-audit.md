## 5. Multi-code semantics: OR/whitelist, not AND

**Verdict: every multi-code field (`jobCd`, `schoolCd`, `sbizCd`,
`plcyMajorCd`) uses OR/whitelist semantics** — a comma-delimited value
means "any ONE of these codes qualifies", not "the applicant must satisfy
all of them simultaneously". This is not assumed from the delimiter alone;
it is corroborated by three independent pieces of evidence from the real
catalog:

1. **Logical necessity for several combos.** E.g. `jobCd =
   "0013001,0013003,0013006"` (재직자=employed, 미취업자=unemployed,
   (예비)창업자=prospective founder) on 희망사다리 장학사업 — employed and
   unemployed are mutually exclusive statuses for one applicant at one
   point in time, so this cannot be an AND-list; it must be "any of these
   three statuses is acceptable".
2. **Zero co-occurrence with 제한없음.** Across all 4 multi-code fields, in
   zero records does a 제한없음(unrestricted) code appear alongside any
   other code in the same combo. If combos were AND-lists, a 제한없음 +
   specific-code combo would be a plausible (if redundant) pattern; its
   total absence is consistent with 제한없음 and multi-code lists both being
   "the acceptable set" in the same slot — never mixed because they'd be
   redundant / self-contradictory under a single consistent OR reading.
3. **"Enumerate-everything" combos function as de-facto 제한없음.** 11
   records set `jobCd` to all 9 non-제한없음 codes at once (e.g.
   `20260313005400212139` "강진품애(愛) 청년 주거비 지원사업", a housing-rent
   support program; `20260904005400211624` "청년재능활동가 지원사업"). These
   are broad welfare/housing programs with no real employment-status
   restriction — enumerating literally every job-status code is
   semantically equivalent to writing 제한없음, which only makes sense under
   OR/whitelist semantics (under AND semantics this combo would be
   impossible to satisfy for anyone).

This OR/whitelist finding governs every compatibility-matrix proposal
below: a target's multi-code value should be treated as "PASS if the
applicant's status compat-matches ANY listed code", mirroring the existing
tri-state `status_compat` operator's per-target PASS/FAIL/UNKNOWN
philosophy (`lib/eligibility/employment.ts`), not a new AND-composition
operator.

## 6. `mrgSttsCd` → `MaritalStatus` mapping proposal

Damoa's `MaritalStatus` (`types/profile.ts`) is 4-way: `single | married |
divorced | widowed`, with distinct onboarding labels (`lib/labels.ts`
`MARITAL_STATUS_LABELS`): single="미혼", married="기혼", divorced="이혼",
widowed="사별". The official codebook is 3-way: 기혼/미혼/제한없음 — it has
**no code for 이혼 or 사별**, and 미혼 in Korean administrative usage means
"never married", not "not currently married" (which would also cover
divorced/widowed). Confirmed via real catalog text: a spot-checked
미혼-targeted policy (`20260318005400212210`, "나만의 특별한 작은 결혼식", a
wedding-support program) is semantically about people who have never
married, consistent with the strict reading.

Proposed safe mapping (design only, not implemented):

| Official code | Label | Damoa `maritalStatus` | Verdict |
|---|---|---|---|
| 0055001 | 기혼 | `married` → PASS; `single`/`divorced`/`widowed` → FAIL | SAFE (eq-like) |
| 0055002 | 미혼 | `single` → PASS; `married` → FAIL; `divorced`/`widowed` → **UNKNOWN** | SAFE for single/married; UNKNOWN for divorced/widowed (없는 코드 대응 — 미혼 doesn't officially cover them, but they aren't demonstrably 기혼 either) |
| 0055003 | 제한없음 | no rule (all pass) | SAFE |

No profile-ontology change needed — this fits a `status_compat`-style
tri-state target spec, analogous to `EMPLOYMENT_TARGET_SPECS` in
`lib/eligibility/employment.ts`, keyed by official code instead of a
parsed Korean phrase.

code) reference table confirmed the CODE SYSTEM's identity — `11680`=서울
강남구, `41135`=경기 성남시 분당구, `26440`=부산 강서구, `50110`=제주시,
`36110`=세종특별자치시, all 100% matches. Internal corroboration: `36110`
alone appears 46× (Sejong has no sub-gu subdivisions, consistent with a
5-digit 시군구-level code), and `50110`+`50130` together appear as a pair
172× (the two 시 that make up all of Jeju).

This proves `zipCd` values ARE 법정동코드(5-digit 시군구-level codes), but
that is **code-system identity, not a safe production mapping**: Damoa's
profile stores province/city as free TEXT (used by the existing `region_in`
operator), not 법정동코드. Turning `zipCd` into a rule would require a new
법정동코드 → Damoa-region-text crosswalk that does not exist in this
codebase today. **Status: UNRESOLVED**, explicitly not proposed for
implementation this phase.

## 13. Proposed Phase 4-B production architecture (design only)

Reuse the existing `CandidateIndex` / `RuleEngine` machinery — **no
separate Youth-specific matcher**. Per-field disposition:

- `mrgSttsCd` → new `status_compat`-style target spec (mirrors
  `lib/eligibility/employment.ts`'s pattern) keyed by official code;
  produces a rule against the existing `maritalStatus` profile field. No
  new operator needed if `status_compat` is generalized to accept a
  code-keyed spec table, OR a small new spec module analogous to
  `employment.ts`.
- `earnCndSeCd === "0043002"` → **unchanged**, already safely handled by
  `buildIncomeRule()`.
- `jobCd`, `schoolCd` → `status_compat`-style multi-code-aware matching per
  §5's OR-composition rule (PASS if any listed code compat-matches PASS,
  FAIL only if all compat-match FAIL, else UNKNOWN) — needs a small
  extension to `status_compat`'s evaluation to accept a comma-delimited
  target value, not a new operator.
- `sbizCd` → **no rule** for any code this phase (per §9, no code is
  currently SAFE besides 제한없음, which needs no rule at all).
- `plcyMajorCd` → **no rule** this phase (no profile field exists; §10).
- `zipCd` → **no rule** this phase (§12, UNRESOLVED).

This keeps every new rule inside the existing `EligibilityRule` /
`RuleEngine` model — no schema changes to `types/benefit.ts` are required
for the SAFE subset (mrgSttsCd, jobCd/schoolCd compat-matches, existing
earnCndSeCd/age rules).

## 14. Proposed `domain/youthCodebook/` module design (design only)

A versioned module mirroring `domain/medianIncome/table.ts`'s conventions:

```
domain/youthCodebook/
  table.ts       // YOUTH_CODEBOOK: CodeFamily[] with apiField, familyId, entries[]
  provenance.ts  // { source, filename, sourceSha256, sourceType: "official_xlsx", verifiedAt }
  types.ts       // CodeEntry { code, officialLabel, canonicalMeaning, implementationStatus }
```

Where `implementationStatus` is one of `"safe" | "compatibility" |
"unsupported" | "unrestricted"` per code (matching this audit's verdicts in
§6–§10), so any future rule-building code can look up a code's status
before deciding whether to emit a rule, rather than re-deriving it from
scratch. `scripts/auditYouthCodebookFrozen.ts`'s `YOUTH_CODEBOOK` constant
is the direct precursor to this module's `table.ts` and can be promoted
into it largely as-is once Phase 4-B is reviewed and approved.

## 15. Proposed dimension-aware `eligibilityDataStatus` semantics (design only)

Current behavior: `eligibilityDataStatus()` returns `"incomplete"`
whenever ANY eligibility group is built (age and/or income), unconditionally.

Proposed (not implemented): track completeness PER DIMENSION
(marital/employment/education/business/region/major), and only promote a
record out of `"incomplete"` when **every** raw field for that record is
either (a) mapped to a SAFE rule, or (b) 제한없음/unrestricted. A single
UNRESOLVED or UNSUPPORTED field anywhere keeps the whole record
`"incomplete"` — never a partial-understanding promotion to
`likely_eligible`. Concretely this could be a small
`resolveYouthDataCompleteness(raw): { complete: boolean; unresolvedFields:
string[] }` helper consulted by `eligibilityDataStatus()`, using the
codebook module's `implementationStatus` per observed code.
